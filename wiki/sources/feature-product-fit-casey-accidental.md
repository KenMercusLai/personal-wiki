## Summary
[[CaseyWinters]] defines [[FeatureProductFit]] as a post-[[ProductMarketFit]] test: a feature must retain its own users, have a scalable adoption path, and improve—or at least not damage—the core product's retention, engagement, or monetization. He argues that feature teams should test with bounded, relevant cohorts, combine behavioral data with user research, and delete features that cannot earn their place. Cases from [[Grubhub]], [[Pinterest]], and [[Netflix]] illustrate adoption tactics, cannibalization, feature removal, and whole-product measurement.

## Key Claims
- Feature usage alone is not success; a feature needs repeat use, scalable adoption, and positive whole-product impact.
- A feature that retains users without improving the core product may be cannibalizing existing value, though neutral cannibalization can be strategically rational when it enables a better long-term product.
- Broadcasting an unproven feature through mass email, universal banners, or press can damage channel performance, activation, or the core experience before value is established.
- Feature experiments should begin with the smallest cohort that can produce a useful signal and should identify the user segment for which the feature works.
- Data analysis and user research answer complementary questions: observed behavior locates friction, while research can explain why users fail to perceive or receive value.
- Product surfaces, notifications, incentives, and customer-support intervention are candidate adoption mechanisms whose fit depends on the product and user.

![Customer tweet reporting that the Grubhub app is not working, illustrating social-media support monitoring](../../wiki-assets/feature-product-fit-casey-accidental/grubhub-social-support-tweet.png)

- Features that never achieve fit, or later lose it, should be repaired or removed rather than preserved because they once shipped.

## Key Quotes
> "Your job is not to get people to use that feature. Your job is to find out if that feature has feature/product fit." — on separating usage pressure from value validation.

> "the feature has to improve retention, engagement, and/or monetization for the core product." — the whole-product requirement.

## Connections
- [[CaseyWinters]] — author and practitioner presenting the framework through Grubhub and Pinterest cases.
- [[FeatureProductFit]] — the article's three-part framework for judging whether a feature belongs in an existing product.
- [[ProductMarketFit]] — analogous company-level model whose retention, monetization, and acquisition logic the feature framework adapts.
- [[Grubhub]] — mobile-app examples involving location accuracy, search-result information, first-order incentives, and social-media support.

- [[Netflix]] — streaming is used as a strategically acceptable cannibalization of DVD-by-mail.
- [[ProductUserSegmentation]] — feature fit should be established for the specific users who retain usage rather than assumed for the entire base.
- [[NotificationDesign]] — notifications can drive adoption when they deliver contextual product value rather than broadcast novelty.
- [[CustomerLifetimeValue]] — Grubhub used persistent mobile-user lifetime value, not only incentive response, to interpret its $10 first-order offer.

## Contradictions
- The source qualifies feature-usage and launch-attention metrics: high adoption created by forced exposure, mass communication, or publicity does not establish feature value and can reduce activation or retention elsewhere.
- The framework is practitioner guidance built from selected company examples. It gives no universal thresholds, experiment durations, causal designs, or method for attributing changes in core retention, engagement, or monetization to one feature.
