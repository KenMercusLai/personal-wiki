## Summary
[[KenWheeler]] reflects on building and maintaining open-source JavaScript projects while serving as Director of Open Source at [[Formidable]]. The essay argues that successful [[OpenSourceProjectMaintenance]] requires useful problem selection, approachable API design, unusually strong documentation, tests, types, release discipline, contributor delegation, and emotional boundaries around public criticism.

## Key Claims
- Open-source work can build personal brand, company reputation, developer skill, community goodwill, and interview opportunities, but it should be chosen because the maintainer actually wants to do it.
- Useful projects usually begin with a concrete problem the author has already felt, then package the solution clearly enough for others to adopt.
- Library API design should balance default usability with necessary configuration and should favor explicit, approachable code over cleverness.
- Documentation, examples, contribution instructions, license choice, tests, types, CI, and release notes are adoption infrastructure, not optional polish.
- Marketing an initial release depends on a clear hook, visual demonstration, timing, and social distribution through channels such as Twitter, Hacker News, Reddit, or a companion blog post.
- Maintainers of popular projects should delegate early, set issue and PR expectations, avoid overreacting to harsh feedback, and protect the core API from narrow edge-case requests.
- Semantic versioning, tags, detailed release notes, deprecation grace periods, and transparent change communication reduce downstream pain for users.

## Key Quotes
