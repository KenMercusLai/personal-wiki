## Definition
[[ProgressiveProductBuilding]] is a personal-project workflow that freezes a small idea after its purpose and use are captured, represents later expansion as linked branches, moves the original idea directly toward implementation, and monitors its delivery state explicitly.

## Current Synthesis
The framework responds to a specific failure mode: repeated product-note refinement can feel like progress while increasing scope, anticipated effort, and the chance that nothing is built. It separates exploration from execution by preserving a Simple Project Idea as a stable origin. If the positioning, generality, or feature set changes materially, the creator makes a linked Complex Project Idea rather than mutating the original. The simple note may gain implementation detail, especially instructions for an AI coding tool, but its next default state is building rather than further ideation. Start dates, deadlines, completion flags, and statuses provide a small portfolio view that makes delay and abandonment visible.

## Key Claims
- Repeatedly elaborating a product idea can enlarge both scope and perceived workload until documentation substitutes for delivery.
- A small idea should retain a stable purpose-and-use core so implementation remains bounded.
- Materially expanded ideas should branch into linked notes instead of silently redefining the original project.
- Technical implementation guidance is the only planned elaboration allowed on the simple idea.
- Immediate implementation creates a stronger default than indefinite backlog cultivation.
- Explicit project metadata makes unfinished, completed, and abandoned ideas visible in one monitored system.
- AI coding leverage can shorten the path from a bounded idea to a working artifact, but does not establish that every project fits a one-day build.

## Evidence
- Failure diagnosis: [[reorx-progressive-product-building-yu-yuan-ren-zhi-lei-bi]] reports that repeated revision made ideas more complex, increased expected workload, and left the author producing product documents rather than products.
- Stable core and branching: [[reorx-progressive-product-building-yu-yuan-ren-zhi-lei-bi]] says a Simple Project Idea should be archived after its purpose and use are captured, while later feature, positioning, or generality changes become linked Complex Project Ideas.
- Implementation constraint: [[reorx-progressive-product-building-yu-yuan-ren-zhi-lei-bi]] allows the simple note to add only a Tech Part intended to support code generation.
- Immediate-build rule: [[reorx-progressive-product-building-yu-yuan-ren-zhi-lei-bi]] proposes implementing a simple idea at once and estimates that some can be built in one day with current vibe-coding tools.
- Portfolio monitoring: [[reorx-progressive-product-building-yu-yuan-ren-zhi-lei-bi]] proposes frontmatter fields for timing, completion, and status, viewed in a table instead of inferred from a large repository list.

## Counterevidence & Qualifications
The framework is a proposed personal practice, not a reported evaluation. It supplies no before-and-after completion rate, quality measure, maintenance record, user feedback, or comparison with other idea systems. A one-day build may be inappropriate for safety-critical, privacy-sensitive, regulated, collaborative, infrastructure-heavy, or poorly understood products, and rapid implementation can turn unresolved product uncertainty into code or maintenance debt. Freezing simple notes and branching every evolution may also fragment context unless naming, status, and archival rules remain clear. The method should therefore be treated as a scope-and-action heuristic rather than a universal product-development process.
